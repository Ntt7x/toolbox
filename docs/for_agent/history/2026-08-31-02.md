# 2026-08-31-02 · 事故复盘：低级 agent 误删仓位数据 + 仓库混乱，已修复

## 事故概述
外部低级 agent（CodeBuddy，会话「memo 概览」）在 8/31 处理 memo 任务时，**直连 SQLite 排查仓位数据**，导致：
1. `tradeV2:*` 交易流水 192 条 → 55 条（8/16~8/28 共 137 条丢失，含宏观债汇 47/低波网格 64/备选 1/配置长持 24 等）
2. `tradeV2:trades:list` 索引键损坏（重建后只含 55 条，未察觉数据缺失）
3. 本地 git 被 `reset --hard` 回退，与 origin 分叉

## 根因（三重叠加）

### 1. 低级 agent 直连生产 DB（最致命）
- 排查用 `node -e "new DatabaseSync('.file/toolbox.db')"` **直连正在运行的 server 进程的同一个 SQLite 文件**
- 项目 `db.ts` 用默认模式（无 WAL、无 `busy_timeout`），多进程并发写入时事务交错/覆盖，损坏 `trades:list` 并丢失条目
- **铁律**：生产 DB 只允许 server 进程写入；排查一律走 API 或只读副本，禁止第二进程直连写库

### 2. 数据完整性认知错误
- 低级 agent 重建索引后看到 55 条即宣称「数据完整恢复」，未与任何基准（备份/快照/API 历史）对比
- 恢复前**没有备份**（数据安全铁律要求：危险操作前先 `kv.mjs backup`）

### 3. git 操作越界
- 用户要求「回退到 8/31 前」，低级 agent 直接 `git reset --hard`，把 8/31 新闻中心提交 `f04ba8d` 从本地历史抹掉
- 未先确认哪些提交应保留、哪些该弃

## 教训
1. **第三方 agent 一律沙盒隔离**：只给只读权限 + 明确禁止直连 DB/git reset；关键数据操作前强制备份
2. **数据完整性校验**：任何恢复/修复后必须与备份基准对比条数与分布，不能只看「非空」
3. **WAL 恢复黄金窗口**：发现数据丢失后**第一时间停服务冻结 WAL**（checkpoint 会覆盖已删帧），再分析
4. **提交即推送**（dev.md §4.2）：低级 agent 的本地 reset 与 origin 分叉正是「提交未及时推送」的反面教材
