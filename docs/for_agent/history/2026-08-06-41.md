# 2026-08-06 41 · 前缀稳定化改造 + 缓存命中率数据模型（降低成本）

## 需求
模仿 Reasonix 的 "Context Append Only for Cache" 设计，服务端 LLM 调用改造降成本：重复使用的提示词放同一 context 命中 DeepSeek 前缀缓存；增加 Cache 命中率数据模型；做 Cache 对比实验。

## 调研结论
- **Reasonix 开源**：github.com/esengine/DeepSeek-Reasonix（MIT，Go）——核心设计 "prefix-cache stability"：常驻指令/系统提示在会话开始加入**稳定前缀**，动态内容**只追加**到用户轮，不重写前缀；模型切换会破坏前缀故禁止
- **DeepSeek 缓存**：完全自动（无 prompt_cache_key 参数），按**前缀完整单元匹配**；chat/completions usage 字段 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`；Responses API `input_tokens_details.cached_tokens`；命中价 ≈ 未命中价 1/50（v4-flash $0.0028 vs $0.14 每 M）；TTL 数小时~数天 best-effort

## 改造
### 前缀稳定化（3 处动态 system → 固定 + 动态进 user）
- reverse-repo.daily：`{date}` → system 固定文本，日期放 user
- reverse-repo.monthly-update：`{months}` → system 固定文本，月份放 user
- watchlist.fundamental：`{code}/{name}/{date}` → system 固定文本，标的+日期放 user
- cbRate/treasuryFx：日期本就在 user（模板无 {date} 占位符）——天然缓存友好，验证即可
- **不覆盖用户编辑的模板**：改 service 组装层，模板占位符在 system 内替换为固定文本

### LLM 封装（core/llm.ts）
- chatCompletion：解析 `prompt_cache_hit_tokens/prompt_cache_miss_tokens`
- chatSearch：解析 `input_tokens_details.cached_tokens`，miss = input - hit
- 契约 `LlmChatResponse.usage` 增加 cacheHitTokens/cacheMissTokens

### 缓存命中率数据模型
- UsageEntry + cacheHitTokens/cacheMissTokens；total/byModule/byDay 聚合 cacheRate
- `/api/llm/usage` 返回；前端 LLM 管理用量监控：总览缓存命中率（hit/miss 输入）+ 按模块命中率 + 说明文案

## Cache 对比实验（真实 key + 真实模板）
- **实验 1**（cbRate system 527 tokens）：第 1 次 48.6% → 第 2/3 次 **97.2% 命中**（miss 仅 15 tokens）
- **实验 2**（reverse-repo.daily 393 tokens）：改造后 第 2/3 次 **97.7% 命中**（384/9）；改造前（日期在 system，逐日变化）3 次全 **0%**
- **成本**：改造后比改造前同场景 3 次输入低 **2.69x**；单次第 2 次起输入成本约省 50 倍（hit 按 1/50 价）
- 注意：短 prompt（~50 tokens）不触发缓存持久化（官方：按固定 token 间隔切单元）——真实场景（数百+ tokens）才有效
