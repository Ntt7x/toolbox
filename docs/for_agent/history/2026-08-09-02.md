# 2026-08-09-02 · Agent Loop Engineering 启发落地 + 前后对比实验

## 会话主题
受《Agent Loop Engineering 控制论设计方案》启发，按"扮演全新 Agent（基线）→ 应用改动 → 扮演资深 Agent（对比）"四步走，验证启发改动的实际价值。

## 完成事项

### Step 1：扮演全新 Agent 用当前环境（基线）
- 按 dev.md §0 开工清单实际走一遍
- **基线发现**：
  1. **遗留 2 个已合入未删分支**（feat/memo-batch4、feat/trade-plan-v2，远程+本地）——新 agent 开工 `git branch -a` 看到 4 个分支困惑"哪个待验收"（§4.1 合并后应删分支的流程执行不严）
  2. **无改动健康检查**：大型 commit（30 文件 +2041/-627、399 行组件重写）直接推，没有人看"改动多大/切到哪些层"
  3. **无收敛信号**：停时 = 用户喊验收，agent 从不主动建议"疑似收敛"
- 顺手修复基线问题：删除 2 个遗留分支（远程+本地）

### Step 2：应用改动（受文档启发）
1. **新增 check-change.mjs**（改动健康检查）：`git diff base` 统计文件数/行数 + 触及分层（core/features/web/docs/scripts）→ 分级建议（PASS/WARN/FAIL + 对照 §5.1 验证级别）——对应范式 V「R_max 预检截断 + 因果半径」
2. **dev.md §6.8「控制效率算账」**：任何控制机制先估 η = 拦截节省/控制器成本，η>1 才做；提示型检查永远值得，拦截型须算账——对应范式 V「效率正性条件」
3. **dev.md §6.4 成本四问 → 五问**：「LLM 自评必配非 LLM 锚」——防裁判兼运动员偏差假收敛——对应范式 V「混合距离/确定性锚」
4. **dev.md §5.1「收敛信号」**：连续全绿 + diff 递减 + 无 open 备忘录 → 主动提示疑似收敛——对应范式 V「停时设计」
5. README 工具表补 check-change

### Step 3：扮演资深 Agent 用改动后的环境（实测）
- check-change PASS 场景：本分支 3 文件/119 行，docs+scripts 无 core → PASS（L2 足够）
- **发现并修复缺陷**：初版只统计 `base...HEAD`（已提交），**工作区未提交改动漏算**——提交前检查典型场景失效 → 改为 `git diff base`（base vs 工作区，含未提交）
- **修复后 WARN 场景实测**：临时 touch core/db.ts → 正确识别 `core=1` → WARN「触及核心层 → 强制 L3 全量冒烟」（exit 1）
- 恢复后回到 PASS

## 对比分析（Step 4）

| 维度 | 改动前（全新 Agent 基线） | 改动后（资深 Agent 体验） | 价值 |
|---|---|---|---|
| 环境整洁 | 4 个分支（2 遗留） | 只有 main + 当前分支 | 消除"哪个待验收"歧义 |
| 改动大小感知 | 无检查，大 commit 直接推 | check-change 提交前自动提示（文件/行数/分层） | 大改动显式过更高级验证 |
| 核心层保护 | 依赖 agent 自觉 | 触及 core/ → 强制 L3 | 核心层改动不可静默 |
| 停时建议 | 纯靠用户 | 客观收敛信号（全绿+递减+无备忘录） | 减少"该验收没验收"的空转 |
| 控制开销 | 0 | 每次提交 +1 次廉价脚本（毫秒级） | η >> 1（提示型，不拦截） |
